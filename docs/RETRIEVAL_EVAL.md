Columns: **Hit@k** = a gold file is among the top k files of the ranking (strict: `gold_files` only). **MRR** = mean reciprocal rank (cut at 10). **Lenient** also accepts `acceptable_files` (prose that legitimately answers the question). **In context** = a gold file is among the sources that fit the 12,000-token budget, i.e. what an LLM would be shown. **Symbols** = share of questions whose gold symbols appear in that context. **Tokens** = mean estimated context size. Configs: `kw=` is the weight of keyword results in the fusion (default 1); `demote tests` multiplies the score of test-file chunks by 0.5 unless the query mentions tests.

## Reading the numbers

_This section is written by hand; `run_eval.py` keeps it when it regenerates the tables above. Numbers quoted here are from the run shown above._

**This evaluation was re-run on 2026-09-30 for the final report.** The `codebase_ai` corpus is this repository, which grew from 74 files (589 chunks) at the first run to 93 files (960 chunks) as M3 to M5 were built, so its numbers moved. Every quoted figure below was updated from the new run. The conclusions held, with one exception: the first run hinted that hybrid puts the gold *function* in context less often than vector (47 against 53 of 57); on the re-run it is 47 against 49, which is nothing to report. That hint is withdrawn.

## Decisions

| Setting | Default | Why |
|---|---|---|
| `RETRIEVAL_MODE` | **`vector`** | Nothing tested beat it. See below. Hybrid and keyword stay available. |
| `TEST_PENALTY` | **`0.5`** | The one change that was a measurable gain and never lost a question. Tests are exempt when the query mentions tests. |

**This reverses my own design.** The architecture document planned hybrid retrieval (vector + keyword, fused with Reciprocal Rank Fusion) as the default. The evaluation does not support that, so the defaults follow the evidence and the design document was updated to say so.

## What the evidence supports

1. **Keyword-only search is clearly worse than vector search on natural-language questions.** MRR 0.593 vs 0.772; the paired difference is -0.178 with a 95% interval of [-0.264, -0.096], and vector was better on 34 questions and worse on 13.
2. **Fusing keyword results into vector results did not help.** Hybrid vs vector: MRR difference -0.034, interval [-0.095, +0.026], better on 17 questions, worse on 18, tied on 50 (sign test p = 1.0). With test demotion on, -0.017 [-0.082, +0.046]. Lowering the keyword weight to 0.5 moves hybrid closer to vector, which is what you would expect if the keyword list only adds noise; no weight was clearly better than vector alone.
3. **Even bare identifier lookups did not favour keyword search.** For a query like `computeCriticalPath`, vector Hit@1 was 86% against 74% for keyword and 77% for hybrid. Keyword search reaches the right file within the top 3 exactly as often as vector (96%) and within the top 5 slightly more often (98% vs 96%), but ranks it first less often. Hybrid with keyword weight 0.5 and test demotion was slightly *worse* than vector with demotion on these lookups (-0.036, interval [-0.071, -0.009]).
4. **Demoting test files is a real, repeatable gain.** Vector: MRR +0.032 (interval [+0.011, +0.057]), better on 10 questions and worse on none. Hybrid: +0.049 ([+0.022, +0.080]), better on 16, worse on none. What fusion "broke" in the first run was mostly keyword search promoting test files and CI configuration above the implementation, and demotion repairs that.
5. **The retrieved context is small.** About 4,600 estimated tokens per question against a 12,000-token budget, and a gold file was in that context for 96% (vector) to 100% (hybrid + demotion) of questions.

## What it does not support

- **Hybrid is not proven useless.** It put a gold file in context for 2 more questions than vector (84 vs 82 of 85; sign test p = 0.5, so not distinguishable from chance) and the specific gold *function* in context about as often (47 vs 49 of 57; better on 1, worse on 3). Whether either matters depends on how answers are generated, which needs the answer-quality evaluation (`eval/run_answers.py`, built in M4 but not yet run on a live model).
- **The demotion gain is concentrated in one repository.** Per repository, vector with demotion vs without: `codebase_ai` +0.098 (better on 8, worse on 0), `magnaflow` +0.004 (better on 2), `rich` +0.000 (the installed package has no tests, so nothing to demote). The repository with a large mirrored test suite benefits a lot; one without tests is unaffected. "Never lost a question" is partly by construction, because no evaluation question asks about tests; the `mentions_tests` exemption covers that case in use, and it is unit-tested but not evaluated.
- **The differences between the top configurations are within noise.** `vector + demote tests` (0.803), `hybrid + demote tests` (0.786) and `hybrid kw=0.5 + demote tests` (0.804) are not distinguishable in MRR. The default is the *simplest* of these, not a proven winner.

## Limits of this evaluation

- **85 questions** (and 57 identifier lookups derived from the same questions, so those are not independent evidence). One question moves a percentage by about 1 to 4 points depending on the repository.
- **All questions are "how does X work" or "where is X" questions, written by the same person.** The evaluation contains no queries built around rare exact strings (an error message, a config value, a magic constant), which is where keyword search traditionally earns its keep. That is the main reason hybrid should be re-tested rather than discarded.
- **Two of the three sets were labelled by the person who built the system** (`magnaflow`, after reading the repo's overview documents; `codebase_ai`, its author). Only `rich` is independent code, and it has no prose and no tests, so it can say nothing about either documentation or demotion.
- **The `codebase_ai` corpus is the live repository**, which changes as the project does (this run indexed 93 files and 960 chunks; the first run, 74 and 589), so its numbers drift between runs. The `magnaflow` and `rich` corpora were static during the evaluation.
- **`acceptable_files` for `magnaflow` were added after the first results**, under a mechanical rule stated in `eval/README.md`. Strict metrics do not depend on them and are the ones used for every decision above.
- **One embedding model** (`bge-small-en-v1.5`). A weaker model might benefit more from keyword fusion.
- **File-level scoring.** A hit means the right *file* was retrieved, not that the right lines were; symbol recall is the only finer-grained signal.
- **Paired statistics treat questions as independent and pool three repositories of different sizes.** Treat the intervals as a guide to which differences are worth believing, not as exact probabilities.

## What to do with this later

- Add rare-exact-string queries to the question sets and re-run `hybrid` against `vector`.
- Run the answer-level evaluation (`eval/run_answers.py`) with a real model: hybrid's small in-context edge may matter differently there.
- A reranker was tried in M4 (`docs/QUALITY_EVAL.md`): the one model tested made things worse, so the Hit@1 (66-71%) vs Hit@5 (96%) gap is still open. Other rerankers, or a different fix for results where prose documents (a changelog, a long guide) outrank the code, would be the next thing to try; it was seen on `psf/requests` in the final demo and has not been evaluated.
