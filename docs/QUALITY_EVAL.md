# Quality evaluation (M4)

M2 chose the retrieval defaults from measurements. M4 added three things that could improve answers, and M5 followed
up on what M4 left open. This document records what the measurements said about each, including the ones that did not
pay off and one earlier figure that turned out to be too optimistic.

| Question | Answer | Evidence |
|---|---|---|
| Does a repository map help questions about the whole project? | **Yes, when it is triggered.** On 11 labelled overview questions the areas shown to the model rose from 63% to 93%. **Recognising such questions is the weak point:** on fresh phrasings written before the patterns were widened, only 2 of 20 were recognised; the widened patterns get 18 of 20, but that number is not independent evidence. | Section 1 |
| Does a cross-encoder reranker improve retrieval? | **No.** The one model tested made retrieval slightly worse and roughly 2 s slower per query. It stays off. | Section 2 |
| Are answers grounded, correctly cited and correct? | **Measured with a local 7B model (30 questions, offline).** Citations are never invented (validity 100%, no made-up locations); with the citation reminder every answer cites its sources (40% to 100% on held-out questions); hand-graded, 14 of 20 answers are correct, 4 partly, 2 wrong. The 4B judge called everything "supported", so no faithfulness number is quoted. | Section 3 |
| Does demoting release notes (CHANGELOG, HISTORY) help? | **No measurable effect:** of 109 questions, 108 tied and one moved by a single rank. Available as `CHANGELOG_PENALTY`, off. | Section 4 |
| Does it scale to big repositories? | **Everything except the embedding model grows linearly** up to 4,000 files (28,000 chunks): 63 s to index, 10 ms to search. The real embedding model dominates, at roughly an hour for 4,000 files on a CPU (extrapolated). | Section 5 |
| Does retrieval hold up on code it was never evaluated on? | **Yes.** 36 questions written blind on `httpx` and `jinja2`: MRR 0.915 and 0.801, the right file in the model's context for every question. | Section 6 |
| Does demoting near-empty chunks (one-line class headers) help? | **No measurable effect:** 140 of 145 questions tied. Not built. | Section 7 |

Follow-up handling (rewriting "and what about retries?" into a standalone question) has no table here: it needs a
model to run, so it is covered by tests with a scripted model only. Its risk is a bad rewrite, which is why the
rewritten question is shown to the user and a rewrite that is empty, cut off or too long falls back to the original.

## 1. Overview questions and the repository map

**What was built.** A question about the whole repository ("what does this project do?") has no single chunk that
answers it. The classifier (`retrieval/query.py`) recognises such questions with explicit patterns, and for them the
retriever adds a generated **repository map** (`retrieval/repo_map.py`) and the top of the README as extra numbered
sources. The map is derived from the index with no model call: directories with file counts and languages, what each
directory's own files define, its package docstring or README title where it has one, the documentation files with
their titles, and the code files that describe themselves. Ordinary questions are untouched.

**How it was measured** (`eval/run_overview_eval.py`). Eleven overview questions were written for two repositories
(`eval/questions/*_overview.jsonl`), each with the directories a good answer needs (`gold_dirs`) and a README or design
document that answers it. *Area coverage* is the share of those directories that
the context shows, either as code from inside the directory or as a line in the map. Each question is run with
ordinary retrieval and with the map.

Run on 2026-10-01 · Windows-11-10.0.26300-SP0 · embedding model `local:BAAI/bge-small-en-v1.5`. Generated by `eval/run_overview_eval.py`.

| magnaflow | plain retrieval | 6 | 0% | 62% | 33% | 83% | 5165 |
| magnaflow | with repository map | 6 | 83% | 87% | 50% | 83% | 7194 |

**Reading it.**

- **Coverage went from 63% to 93%.** Every question the classifier recognised reaches 100% (the 10 of 11 it now
  recognises); the one it does not (*"What are the main moving parts outside the React app...?"*, arguably scoped to part
  of the repository) is unchanged from ordinary retrieval.
- **The classifier needed more work than first reported.** The first version recognised 7 of 11 of these questions, and I
  reported that as 64% "not tuned on them". That figure was optimistic: those questions were phrased close to the
  patterns I had just written. To measure properly, 20 overview questions and 24 narrow ones that merely *sound* like
  overviews (`eval/questions/classifier_heldout.json`) were written in varied phrasing **before** the patterns were
  widened. The first version recognised **2 of 20 (10%)** of them and wrongly flagged 1 of 24. That is the honest
  figure for fresh phrasings.
- **The patterns were then rebuilt by intent** (what is it, what is it for, what kind of thing it is, an overview or tour,
  how it is structured, its main parts, how the pieces fit together, what it is built with, where to start), each with
  a guard that rejects the question when what follows narrows it to one part ("an overview *of the cart*").
  Afterwards: 10 of 11 on the development questions, **18 of 20** on the held-out set, 0 of 24 narrow ones flagged and
  **0 of 109 labelled specific-code questions** flagged. **Treat 18 of 20 as a regression guard, not as independent
  evidence:** the held-out items were written by the same person who then wrote the patterns, with those items in view.
  A genuinely fresh measurement needs questions written by someone else. `eval/check_classifier.py` does that
  measurement in seconds on any file of your own phrasing, and the two it still misses (*"Where does the main logic live,
  broadly speaking?"*, *"What's in the src directory versus the tests?"*) show the kind of question that is not covered.
- **A missed overview question costs little and a false one costs a bit more.** A miss gets ordinary retrieval, exactly
  as before M4. A narrow question that got the map would be answered from a slightly less relevant context, which is why
  the patterns lean towards precision.
- **The cost is about 1,700 more tokens of context** on average across the eleven questions (6,824 against 5,106).
- **This metric is generous by construction.** A directory counts as covered when the map *names* it, and the map names
  every directory it lists. Coverage says the model was told the areas exist, not that its answer explains them well.
  Whether the answers are better needs real answers and a judge (section 3).
- **The sample is small and one of the two repositories is this project.** Eleven questions across two repositories.
  Treat the direction as credible and the exact percentages as rough.

## 2. Reranking

**What was built.** An optional cross-encoder (`retrieval/reranker.py`, `RERANKER_MODEL`) that re-orders the top 30
candidates after vector search. Test files stay demoted after re-ordering. It is off by default and only worth turning
on if it helps.

**How it was measured** (`eval/run_rerank_eval.py`). The 85 natural-language questions of the three M2 suites, with the
current default retrieval as the baseline, and the same retrieval followed by the reranker, compared question by
question. One model was tested: `cross-encoder/ms-marco-MiniLM-L-6-v2` (about 90 MB, run on CPU).

**Reading it.**

- **It made things worse, not better.** Pooled MRR fell by 0.037 (the interval, -0.095 to +0.023, includes zero, so
  the honest statement is "no improvement, probably a small loss"). It helped on 9 questions and hurt on 17. On this
  project's own questions the loss was large and the interval excludes zero (-0.122, interval -0.240 to -0.016).
- **It is slow on a CPU:** roughly 2 seconds more per query (1.7 s in the final run, 2.8 s in an earlier one on the same machine), against about 30 milliseconds for the whole of retrieval.
- **Decision: it stays off by default.** The code, the setting and the tests remain, so it can be tried with another
  model without new work.

  rerankers were not downloaded, so nothing here says they would not help. Retrieval was already strong (96% Hit@5),
  which leaves a reranker little room; a repository where the right file is often ranked 10th to 30th might behave
  differently. The `codebase_ai` suite indexes this repository as it is now, so it is re-run with every report.

## 3. Answer quality, measured with a local model (2026-10-06)

**What was run.** The first real answers this system ever produced: 30 labelled questions answered fully offline by
`qwen2.5-coder:7b` through Ollama 0.35.1 (the configured local default; about 41% on a 4 GB GTX 1650, the rest on the
CPU), graded by `gemma3:4b`, a model from a different family. Nothing left the machine. Questions: the first 10 of
`magnaflow` (a JavaScript application), the first 10 of the blind `httpx` set, and the first 10 of the blind `jinja2` set
twice, once without and once with the citation reminder described below. About 2 minutes per answer.

**First run: 20 questions, the original prompt.**

| Measure | `magnaflow` (10) | `httpx` (10) | All 20 |
|---|---|---|---|
| Answered without error | 10 | 10 | 20 |
| Grounded: cites at least one supplied source | 60% | 70% | **65%** |
| Citation validity: cited numbers that exist | 100% | 100% | **100%** |
| Citation precision: cited sources that are relevant | 58% | 67% | 63% |
| Cites a gold or acceptable file | 30% | 60% | 45% |
| Mentions a location it was not shown | 0% | 0% | **0%** |
| Refused / cut off | 0% / 0% | 0% / 0% | 0% / 0% |
| Tokens in / out per answer | 4,871 / 138 | 4,518 / 281 | 4,694 / 209 |

**Correctness, graded by hand against the code** (by the AI assistant that built the system, not by an independent
person; a strict reading of whether the answer is right, not only whether it matches what it cites):

| Grade | Answers | Notes |
|---|---|---|
| Correct | 14 of 20 | including the `MockTransport` question, whose file retrieval had ranked below 5th; it was still in the context, and the model found it and cited the exact lines |
| Partly correct | 4 | forgets one of six roles; misses the actual `seatsUsed <= seatLimit` check; places decompression imprecisely; claims query-parameter merging combines values (the code it quotes keeps only the new one) |
| Wrong | 2 | explains where @mentions are highlighted, not where they are matched to a person; says reminders are sent by `functions/index.js`, which is dead Cloud Functions code (MagnaFlow sends them from a GitHub Actions job) |

**What it found.**

- **A third of the answers cited nothing.** The content of most was right, but the 7B model named files in prose
  ("`src/lib/criticalPath.js`") instead of writing `[n]`. Citation validity was perfect and no answer invented a location,
  so the problem was missing citations, not false ones.
- **Faithful is not the same as correct.** Both wrong answers are faithful to the code they cite: retrieval supplied
  plausible but wrong code (a highlighting function; an undeployed Cloud Function), and the model described it
  accurately. The checks in this project, and the judge, measure faithfulness. Nothing here can know that code is dead.
- **The 4B judge is uninformative.** It called every one of the 33 answers it judged `supported`, including ones that
  claim more than their cited excerpts show. A faithfulness score from it would read 100%, so none is quoted. A stronger
  judge, or the hand check below, is needed for that number.

**The fix it led to: a citation reminder.** Small models follow what is nearest the end of the prompt, so one line was
added after the question: *"Answer only from the sources above, and cite every statement about the code with its number,
like [1]."* (`rag/prompts.py`). To test it without tuning on the questions that revealed the problem, the first 10 blind
`jinja2` questions were answered with the old prompt and then with the new one:

| `jinja2`, same 10 questions | Without the reminder | With it | Paired |
|---|---|---|---|
| Grounded | 40% | **100%** | better on 6, worse on 0 (sign test p = 0.03) |
| Cites a gold file | 30% | **100%** | better on 7, worse on 0 (p = 0.02) |
| Citation precision | 56% | 79% | |
| Correct / partly correct / wrong (hand graded) | 8 / 2 / 0 | 7 / 3 / 0 | one answer each way; no measurable change |
| Tokens out, seconds per answer | 239, 112 s | 219, 112 s | |

**Decision: the reminder is on.** It fixed missing citations without measurably changing correctness or cost. **What
this does not show:** ten questions are few (the p-values say the direction is unlikely to be chance, not how large the
effect is); the reminder was not re-run on the first 20 questions; Claude and OpenAI were still not run, and a hosted
model may already cite reliably without it.

**The hand check is still open.** `eval/results/answers_magnaflow_sample.md` and `answers_httpx_sample.md` hold 10 judged
answers, each with the code it cites, and without the judge's verdicts. Grading them and running `--check-sample`
(below) measures how far the judge can be trusted; until then the faithfulness column stays empty.

**How it was run** (both models local, so nothing is sent anywhere and no `--yes` is needed):

```bash
ollama pull qwen2.5-coder:7b && ollama pull gemma3:4b
LLM_TIMEOUT_SECONDS=600 python eval/run_answers.py path/to/repo eval/questions/httpx.jsonl \
    --provider ollama --model qwen2.5-coder:7b --judge-provider ollama --judge-model gemma3:4b \
    --limit 10 --export-sample 5
```

`LLM_TIMEOUT_SECONDS=600` matters on a laptop: the first word of an answer only arrives after the whole prompt has been
read, which took over a minute on this hardware, and the default 120 s leaves little margin.

### What the harness measures

**What was built** (`src/codebase_ai/answer_eval.py`, `eval/run_answers.py`). It answers the labelled questions with a
real model and scores the answers:

- **Grounded rate:** the answer cites at least one supplied source.
- **Citation validity:** cited numbers that refer to a source that was actually supplied.
- **Citation precision:** cited sources that are relevant (a gold or acceptable file, a file under a gold directory, the
  map for an overview question, or code that contains a gold symbol).
- **Cites a gold file**, **supplied sources left uncited**, **locations mentioned that were never shown**, refusals and
  truncations.
- **Faithfulness (optional, needs a judge model):** is the answer supported by the code it cites? The judge sees only
  the question, the answer and the *cited* excerpts, and returns `supported`, `partially_supported` or `unsupported`
  with the claims it could not back. An answer with no citations is not judged (there is nothing to check it against);
  the grounded rate already counts it.

The scoring, the judge prompt and reply parsing, error handling (a rejected key stops the run, a transient failure is
recorded and the run continues) and the script itself, including its refusal to start without `--yes` when code would
be sent to a hosted provider, are also covered by tests with scripted models. Each result keeps the code it cites, so
the hand-check file can be graded on its own.

**How to run it with a hosted model.**

```bash
python eval/run_answers.py path/to/repo eval/questions/magnaflow.jsonl \
    --provider anthropic --model <answering model> \
    --judge-provider openai --judge-model <a different model> \
    --limit 20 --export-sample 10 --yes
```

It prints exactly what it will do (number of calls, tokens of retrieved code per prompt, where code is sent) and does
not start without `--yes` when either model is hosted. Use a judge from a different model family than the answerer
where you can: a model grading its own answers is lenient, and the plan warns when they are the same.

**Checking the judge.** A model's verdict is an opinion. `--export-sample N` writes N judged answers to a markdown file
*without* the judge's verdicts. Grade them yourself against the cited code, save your verdicts as JSON
(`{"<id>": "<verdict>"}`), and run

```bash
python eval/run_answers.py --check-sample my_verdicts.json --results eval/results/answer_eval.json
```

to see how often you and the judge agree. Faithfulness numbers are only worth quoting alongside that agreement rate.

## 4. Release notes: does demoting them help?

**Why this was tried.** On `psf/requests`, a question about redirects ranked the project's changelog (`HISTORY.md`)
above the code that implements redirects. Test files are already demoted; release notes seemed the same kind of file
that is rarely the answer to "how does X work". `Retriever(changelog_penalty=...)` (setting `CHANGELOG_PENALTY`) scales
the score of CHANGELOG, HISTORY, NEWS, RELEASES and release-notes files (only documents, never code files named
`history.py`), unless the question itself is about releases or changes.

**How it was measured** (`eval/run_changelog_eval.py`). 24 labelled questions about `requests`
(`eval/questions/requests.jsonl`: 20 about the code and 4 that really are about releases, which must not be hurt), plus
the 85 questions of the earlier suites, which have no release notes and so show that nothing changes where the feature
does not apply. The questions were written after seeing the problem, which favours the feature; it still did not help.

## 5. Scale: how big a repository can it handle?

**What was measured** (`eval/scale_test.py`). Synthetic Python repositories of 200, 1,000 and 4,000 files, indexed with a
cheap hash-based embedder that produces vectors of the real size, so that everything *around* the embedding model is
timed: walking, parsing, chunking, the SQLite and Chroma writes, searching, and an incremental re-run with nothing
changed. The last column extrapolates the real embedding step from the rate seen when `psf/requests` was indexed
for real (786 chunks in 100 seconds, about 7.8 chunks per second on this laptop CPU, model loading included).

| Files | Chunks | Index (no embedding model) | Re-run, nothing changed | Vector search | Keyword search | Index size | Embedding with the real model (extrapolated) |
|---|---|---|---|---|---|---|---|
| 200 | 1,400 | 2.5 s | 0.1 s | 4 ms | 2 ms | 6 MB | about 3 min |
| 1,000 | 7,000 | 13.8 s | 0.5 s | 5 ms | 10 ms | 22 MB | about 15 min |
| 4,000 | 28,000 | 62.9 s | 2.1 s | 10 ms | 36 ms | 85 MB | about 60 min |

**Reading it.**

- **Nothing grows faster than the repository.** Indexing time and index size are linear in the number of chunks (about 3
  KB per chunk); an unchanged re-run costs about 2 seconds at 4,000 files; vector search stays in the tens of
  milliseconds, and keyword search grows with the chunk count (36 ms at 28,000 chunks).
- **The embedding model is the bottleneck, and it is hardware-dependent.** At the rate seen here, a 4,000-file repository
  takes about an hour to index the first time on a CPU; every later run only re-embeds changed files. A GPU or a hosted
  embedding provider changes this a lot.
- **What this does not show.** The code is synthetic: no giant files, deep nesting or unusual structures. The embedding time
  is an extrapolation, not a measurement. Nothing was run on a repository of tens of thousands of files, and memory use
  was not measured.

## 7. Near-empty chunks (2026-10-06)

**Why this was tried.** For a vague question, chunks with almost no content can rank high: a large class without a
docstring becomes a one-line class chunk (`class Response:`), and a type alias between definitions a two-line module
chunk. Their embedding is dominated by the `path • symbol • kind` header, so it matches vague queries easily.

**How it was measured.** The default retrieval against the same retrieval with chunks of at most one or two non-blank
lines demoted (score x0.8 or x0.6), on all 145 labelled questions of six repositories (`magnaflow`, `codebase_ai`,
`rich`, `requests`, `httpx`, `jinja2`) and their 110 identifier lookups, compared question by question.

| Demotion | Questions: MRR difference | 95% interval | Better / worse / tied | Lookups: MRR difference |
|---|---|---|---|---|
| at most 1 line, x0.8 | +0.000 | [+0.000, +0.000] | 1 / 0 / 144 | -0.002 |
| at most 2 lines, x0.8 | -0.003 | [-0.013, +0.004] | 4 / 1 / 140 | +0.003 |
| at most 2 lines, x0.6 | -0.003 | [-0.013, +0.004] | 4 / 1 / 140 | -0.006 |

**Decision: not built.** It changes almost nothing, because a near-empty chunk rarely pushes the right *file* down:
it takes one of the context slots, not the file's place in the ranking. It stays a cosmetic problem of vague,
whole-project questions, where the repository map carries the answer anyway. (Measured with a one-off script around
`Retriever.rank`; the method is the paired comparison used everywhere else.)

## Decisions recorded here

- Overview questions use the repository map (on by default, `USE_REPO_MAP`). Recognition was 10% on fresh phrasings
  before the patterns were widened and is 90% afterwards on the same items (not independent); no labelled specific-code
  question is misclassified (0 of 109).
- The reranker is off by default (`RERANKER_MODEL` unset), because the only model tested did not help.
- Release-note demotion is off by default (`CHANGELOG_PENALTY=1`), because it made no measurable difference.
- The locate / explain split of the original design was not built: nothing would behave differently, so it would be
  dead code. Only "overview or not" changes what happens.
- Repository-map summaries written by a model were not built. The deterministic map costs nothing per question and
  cannot be wrong about what a directory contains; a model-written version is worth trying only if answers to overview
  questions turn out to be weak.
